## 2. Arquitetura e Stack Tecnológico
* **Hospedagem / Controle de Versão:** GitHub (GitHub Pages para frontend, se aplicável).
* **Banco de Dados & Backend:** Supabase (acessado via Supabase JS Client via API REST/PostgREST).
* **Frontend:** HTML5, CSS3, JavaScript (Vanilla/ES6+).
* **Regra de Dependências:** É **ESTRITAMENTE PROIBIDO** o uso de empacotadores (NPM, Webpack, Vite) ou frameworks SPA (React, Angular, Vue). Toda e qualquer biblioteca de terceiros deve ser importada exclusivamente via `<script src="...CDN...">`.

## 3. Bibliotecas Permitidas (Via CDN)
Para reduzir a verbosidade do código, evitar erros nativos e focar na regra de negócio, utilize as seguintes bibliotecas via CDN:
* **Supabase Client:** `@supabase/supabase-js` (Para interagir com o DB facilmente).
* **Biometria e Vivacidade:** `face-api.js` (Para detecção facial e comparação de descritores no frontend, utilizando os modelos leves).
* **Ícones:** `Lucide Icons` ou `Phosphor Icons` (Carregados via CDN para manter a interface limpa sem usar emojis).
* **Manipulação de Tempo:** `Day.js` (Biblioteca levíssima para facilitar cálculos de horas, atrasos e formatação).

## 4. Diretrizes de UI / UX
* **Público-Alvo do Dispositivo:** Exclusivo para uso em Tablets (totem na recepção da empresa) ou Desktop. Não é necessário focar em responsividade para telas de celulares pequenos.
* **Estilo Visual:** Design limpo (Clean UI), minimalista e corporativo.
* **Cores:** Fundo estritamente **Branco** (`#FFFFFF` ou `#F8F9FA`). Tipografia em tons de cinza escuro/preto para alto contraste. Cores de destaque (sucesso/erro/aviso) devem ser usadas apenas em botões, alertas e tickets.
* **Ícones vs Emojis:** É **PROIBIDO** o uso de emojis na interface. Utilize exclusivamente a biblioteca de ícones escolhida.
* **APIs Nativas:** Utilizar `navigator.mediaDevices.getUserMedia` EXCLUSIVAMENTE para acessar a câmera no momento do registro.

## 5. Especificações de Negócio (Comportamento Esperado)

### 5.1. Fluxo Principal de Entrada
* O sistema exibe um campo para inserção da Matrícula.
* Ao avançar, liga a câmera. O sistema usa `face-api.js` para validar se há um rosto real e compara com o banco de dados.
* Em caso de sucesso, registra o log `IN` usando o horário do servidor do Supabase (`NOW()`).
* **UI:** Exibe "Entrada feita com sucesso" e mostra um ticket na tela contendo Matrícula, Data e Horário.

### 5.2. Fluxo Principal de Saída
* Funciona de forma similar, solicitando a Matrícula. A foto no momento da saída não é obrigatória, apenas a confirmação.
* Ao confirmar, registra o log `OUT` com o horário do servidor.
* **UI:** Exibe "Saída registrada com sucesso" e mostra um ticket contendo: Matrícula, Horário de Entrada, Horário de Saída e Total de horas trabalhadas.

### 5.3. Regras de Exceção e Tolerância
* **Saída sem Entrada:** Se o funcionário tentar registrar saída sem um log `IN` no dia, o sistema BLOQUEIA o registro padrão. O status do funcionário no dia vai para `SUSPENDED` e a interface exibe um aviso informando que o caso foi encaminhado para análise (departamento superior).
* **Tolerância de Atraso:** A jornada padrão inicia às 08:00. Há 15 minutos de tolerância.
* **Penalidade de Atraso:** Se a entrada for registrada após as 08:15 (ex: 08:16), o sistema grava o ponto normalmente, mas insere `1` ponto na tabela `penalty_points` com o motivo de atraso.
* **Acúmulo de Pontos:** Sempre que a tabela `penalty_points` somar 5 ou mais pontos no mês para uma Matrícula, o sistema deve registrar a flag de "Alerta Disciplinar" (pode ser um campo na tabela `employees` ou um log de notificação no banco).

### 5.4. Faltas
* **Falta Integral:** Ao final do dia (ex: executado via primeira interação do dia seguinte ou cron job no banco), se um funcionário ativo não tiver nenhum registro `IN` no dia anterior, ele recebe `1` ponto na tabela `penalty_points` por Falta Não Justificada e o status diário vai para `ABSENT`.
